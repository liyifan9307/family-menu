## 1. 背景与目标

### 1.1 背景

调研显示（详见 `docs/research/family-app-research.html`）：**共享日程 / "谁去接"是唯一被市场反复验证的家庭高频刚需**。国内「卷了么」小程序（杭州宝爸为 4 岁娃开发）上线一个多月即有五六百家长使用，深度用户**每天打开 2–3 次**，核心价值不是"排课程表"，而是**消除家庭成员之间的信息交接**。

本项目的典型场景与之高度重合：父母上班、父母长住带娃（早送下午接）、4 岁孩子、老人参与接送。当前痛点是——谁去接、几点、在哪里、今天有没有变更，全靠微信口头问，容易忘、容易记错、老人看不到。

### 1.2 目标

| 目标 | 衡量方式 |
|---|---|
| 让接送安排"写一次、全家人都看到" | 家庭成员查看覆盖率 ≥ 80%（加入家庭的成员中，至少 80% 在上线首月打开过日程页） |
| 减少口头交接 | 上线 4 周后，问卷回收中"仍需要口头确认接送"的比例 < 40% |
| 老人不用注册也能看 | 只读分享链接打开查看率 ≥ 60% |
| 录入足够快 | 单次新增日程 ≤ 3 步、≤ 15 秒（可用埋点计时验证） |

### 1.3 非目标（本期明确不做）

- 不做家务分工 / 积分 / 值日表（情绪与考核风险，见调研结论）
- 不做家庭账本、相册、成长记录
- **不做定时提醒**（Q-4 已确认：只做变更即时通知，当天 08:00 提醒不做）
- 不做周期重复规则的复杂配置（如"每隔周二的隔周"），一期只做单次 + 简单每周重复
- 不做与学校课表 / 日历的双向同步

## 4. 需求描述（EARS）

> 前缀约定：**U**=Ubiquitous 始终约束、**E**=Event-driven 事件触发、**X**=Unwanted 异常、**S**=State-driven 状态驱动、**O**=Optional 可选。

### 4.1 数据与权限

- **[U-01]** 系统**始终**要求所有日程记录携带 `familyId`；所有读写必须经云函数，前端不得直连数据库。
- **[U-02]** 系统**始终**在云函数入口用 `openid + familyId` 校验调用者是该家庭 active 成员，非成员调用返回 `NOT_MEMBER`，成员操作越权返回 `NO_PERMISSION`，且不泄露任何日程内容；**只读分享链路例外，仅凭有效 token 访问**（见 U-06）。
- **[U-04]** 系统**始终**允许家庭内任一 active 成员新增日程，不因角色非管理员而拒绝（Q-2）。编辑与删除权限仍限创建人或管理员。
- **[U-05]** 系统**始终**在分享图片与只读页中展示完整的孩子姓名与详细 `place` 字段，不做截断或打码（Q-5）。
- **[U-06]** 系统**始终**要求只读分享链接携带有效 token；token 仅授权其绑定 `familyId + date` 的当日日程，不授权任何其他日期或家庭数据。
- **[E-01]** 当用户切换家庭时，系统**应当**清空当前页面的日程列表与本地分页游标，并以新 `familyId` 重新拉取，避免残留上一个家庭数据。
- **[X-01]** 如果云函数返回 `NOT_MEMBER` 或 `FAMILY_NOT_FOUND`，则系统**应当**停止渲染、提示"无权查看该家庭日程"，并跳转回身份引导页重新登录，不得展示空列表冒充"无日程"。

### 4.2 日程列表

- **[U-03]** 系统**始终**按 `date + timeStart` 升序展示日程；跨天数据互不混排。
- **[S-01]** 当处于"今天"视图且无任何日程时，系统**应当**展示空态提示"今天还没有安排，点右下角加一条"，而不是空白页。
- **[S-02]** 当日程被标记"已完成"时，系统**应当**在列表中降低其视觉权重（文字变色 + 时间保留），但**不得**从列表移除，便于回看。
- **[E-02]** 当用户下拉刷新或重新进入主页卡片时，系统**应当**重新拉取当天数据；若距上次成功拉取不足 30 秒，可直接用缓存并静默后台刷新。

### 4.3 新增与编辑

- **[E-03]** 当用户提交新增日程时，系统**应当**展示保存中状态，在云函数确认写入成功后返回列表；失败保留草稿，超时复用同一 requestId 确认结果。
- **[E-04]** 当用户保存日程变更时，系统**应当**记录 `updatedAt`，并向变更涉及的负责人推送一条"日程已变更"通知。
- **[X-02]** 如果用户提交时必填项（日期、开始时间、事项）为空，则系统**应当**在对应字段下方给出具体提示，不得提交到云端。
- **[X-03]** 如果网络异常导致提交失败，则系统**应当**保留用户已填写的表单内容并提示"保存失败，内容已保留"，不得清空重来。
- **[S-03]** 当用户编辑一条非本人创建、且自己不是管理员的日程时，系统**应当**只读展示，隐藏编辑/删除入口（Q-2：新增不受此限）。
- **[O-01]** 在用户选择"每周重复"的情况下，系统**应当**一次性生成未来 4 周内的 4 条独立记录，每条可单独修改或取消，且不影响已生成的其他记录。

### 4.4 通知、分享与只读页

- **[E-05]** 当新增日程指定了负责人且负责人不是创建人时，系统**应当**向该负责人推送订阅消息，内容含"时间 + 事项 + 地点"。
- **[E-06]** 当用户点击"转发图片"时，系统**应当**生成当日日程图片并写入相册，成功后提示"图片已保存，可发到微信"；图片内容按 U-05 包含完整姓名与门牌。
- **[E-08]** 当用户点击"分享给家人"时，系统**应当**通过云函数生成 token 并拼接只读页链接；分享卡片标题为"{{家庭名}} {{所选日期}}的接送安排"。
- **[E-09]** 当老人通过分享链接打开只读页时，系统**应当**凭 token 拉取对应 `familyId + date` 的日程，且页面只保留查看能力——不展示新增、编辑、完成标记、切换家庭等任何写入口。
- **[X-04]** 如果用户未授权相册写入权限，则系统**应当**提示手动授权路径，不得静默失败。
- **[X-05]** 如果用户未订阅消息或订阅已过期，则系统**应当**在保存日程后提示"想让家人收到提醒，需先开启通知"，并提供跳往设置页的入口，但**不得**阻断保存本身。
- **[X-07]** 如果只读页 token 不存在、已过期或家庭已解散，则系统**应当**展示"链接已失效，请让家人重新分享"，不得展示旧数据或跳回主流程。
- **[S-04]** 当处于只读页状态时，系统**应当**禁用所有写操作的云函数入口（后端按 token 权限再校验一次），前端隐藏只不算完成，必须云端强制。
- ~~**[O-02]** 当天 08:00 定时提醒~~ — **已按 Q-4 删除，本期不做**。

### 4.5 成员变更联动

- **[E-07]** 当成员被移出家庭时，系统**应当**立即撤销其访问该家庭日程的权限；已发出的只读分享 token 同时失效。
- **[X-06]** 如果家庭被解散，则系统**应当**先原子标记家庭为解散中并撤销访问，再分批清理家庭全部日程、分享与关联记录；清理可重试，全部完成后才报告解散完成。

## 5. 流程与交互

### 5.1 主流程

```
打开小程序 → 身份三态判断（复用 login）
   ├─ 有家庭 → 主页 → 「家庭日程」卡片 → 当日列表
   └─ 无家庭 → 身份引导页（既有逻辑，不变）

日程页：
  查看当日列表 ──加一条──→ 一屏表单 ──保存──→ 云函数写入 ──→ 即时通知负责人
       │                                   │
       ├─分享给家人─→ 生成 token ─→ 只读页（老人点开，无需注册）
       └──转发图片──→ canvas 生成图片 ──→ 保存相册 ──→ 微信发给家人
```

### 5.2 交互要点（对齐调研原则）

| 点 | 要求 |
|---|---|
| 入口 | 主页卡片（Q-1）：卡片上直接露今日条数与首条时间，点进去看详情；不加 Tab，不动 tabBar |
| 录入快 | 表单一屏完成，不跳页；日期默认今天、时间默认整点、负责人默认自己；地点支持从历史地点中快速选 |
| 一眼看清 | 列表首屏优先显示"时间 + 事项 + 地点"三要素；负责人用 `co_member.color` 色点标识，与家庭成员列表视觉一致 |
| 家人查看 | 双通道（Q-3）：① 分享链接点开进入只读页，无需注册；② 可发送日程图片。只读页采用全站字号规范 |
| 分享内容 | 按 Q-5 显示孩子姓名 + 详细门牌；分享 token 7 天过期，仅发家庭小群（见开头风险提示） |
| 变更留痕 | 修改/取消保留 `updatedAt` 与操作人，列表可展开查看，避免"谁改的"扯皮 |
| 状态清晰 | 待办 / 已完成 / 已取消三态用颜色 + 文案双重标识，不只靠颜色区分 |

| 页面 | 路径 | 说明 |

## 6. 数据结构建议

**成员体系统一用 `co_member`（Q-6）**，不新建成员表，避免 `dish_members` 那种双轨分叉。日程写入集合 `co_schedule`，分享链路新增集合 `co_schedule_share`；均为空集合起步，读写只走云函数，权限"仅管理端可读写"。

### 6.1 `co_schedule`

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 自动生成 |
| `familyId` | string | 必填，归属家庭 |
| `date` | string | `YYYY-MM-DD`，按日查询主键 |
| `timeStart` | string | `HH:mm`，必填 |
| `timeEnd` | string | `HH:mm`，可选 |
| `title` | string | 事项，必填，≤ 30 字；写入前走 `checkText()` |
| `childName` | string | 孩子姓名，用于分享展示（Q-5） |
| `place` | string | 详细地点/门牌，可选，≤ 50 字（Q-5：完整展示） |
| `ownerOpenid` | string | 负责人 openid，默认创建人；对应 `co_member.openid` |
| `createdBy` | string | 创建人 openid |
| `status` | string | `pending` / `done` / `cancelled` |
| `repeatRule` | string | 可选，`none` / `weekly` |
| `updatedAt` | number | 毫秒时间戳，变更时写入 |
| `createdAt` | number | 毫秒时间戳 |

### 6.2 `co_schedule_share`（Q-3 新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 自动生成 |
| `token` | string | 随机 token（建议 16 位以上，不用 `Math.random()`），唯一索引 |
| `familyId` | string | 绑定的家庭 |
| `date` | string | 绑定的日期，只读页仅能看这一天 |
| `createdBy` | string | 生成人 openid |
| `expiresAt` | number | 毫秒时间戳，生成后 7 天 |
| `createdAt` | number | 毫秒时间戳 |

### 6.3 索引建议

| 集合 | 字段 | 类型 |
|---|---|---|
| `co_schedule` | `familyId` + `date` | 复合普通 |
| `co_schedule` | `familyId` + `date` + `status` | 复合普通 |
| `co_schedule` | `ownerOpenid` + `date` | 复合普通（推送查询） |
| `co_schedule_share` | `token` | **唯一** |
| `co_schedule_share` | `familyId` + `date` | 复合普通 |

**云函数建议**：独立 `scheduleService`，action 至少包含 `listByDate` / `create` / `update` / `setStatus` / `createShareToken` / `getSharedByToken` / `generateShareCode`（图片由客户端生成）。沿用 `familyService` 的双参数归属校验与错误码风格；`getSharedByToken` 是唯一不校验 active 成员的入口，只校验 token 有效性与绑定范围。

## 8. 验收标准

| # | 验收项 | 预期结果 |
|---|---|---|
| AC-1 | 新增一条日程，另一台设备（另一成员）刷新后可见 | 满足验收项描述；待执行 |

## 10. v0.3 补充规则（2026-11-25）

本节优先于前文同主题描述；保留 Q-1～Q-6 已确认决策。本版为用户授权补全文档后的默认实施方案，未表示已开发或已测试。

### 10.1 首版边界与权限

首版实现 F-1～F-7（含完成标记），F-8 每周重复、F-9 本周概览后续实现，首版隐藏重复开关。后续重复按所选日期及其后 7/14/21 天生成四条，独立操作，不引入整组修改。

| 操作 | 普通有效成员 | 创建人 | 负责人 | 管理员 | 分享访客 |
|---|---|---|---|---|---|
| 查看 / 新增 / 分享 | 是 | 是 | 是 | 是 | 仅查看绑定日期 |
| 编辑 / 删除 | 否 | 是 | 否 | 是 | 否 |
| 完成 / 取消 / 恢复待办 | 否 | 是 | 是 | 是 | 否 |

角色权限取并集，所有写操作须仍为有效成员。状态允许 pending→done/cancelled、done/cancelled→pending；恢复必须确认。取消保留记录及原因（选填），删除为软删除并二次确认，列表与分享均排除已删除项，首版不提供删除恢复。

### 10.2 数据与交互

孩子姓名首版为选填文本，不建儿童账户或选择器；空值不显示。地点选填，历史地点仅取当前家庭未删除日程最近使用的十个去重值。备注选填、最多 200 字；结束时间选填且必须晚于开始时间，首版不支持跨午夜，提示拆成两天。事项 30 字、地点 50 字、孩子姓名 20 字，去首尾空格后按 Unicode 字符计数，前后端一致。

日期使用 Asia/Shanghai 日历日，时间使用 24 小时制。今天默认开始时间为下一整点；23 点后默认 23:59，用户可调整。无历史日程也能直接填写。常用字段直接显示，结束时间和备注置于“更多信息”；表单允许滚动，不将一屏作为小屏硬约束。15 秒目标为预填信息充分的常用场景。

首页展示最近一条待办（优先尚未到时的待办，否则最早未完成待办），全部结束显示“今天的安排已结束”；总条数不含已删除记录。完成和取消仍在列表保留。编辑页只展示当前角色有权执行的按钮。

### 10.3 刷新、分享与通知

首版不承诺跨设备自动实时推送列表；进入页面、切换日期、回到前台和下拉刷新获取最新数据。缓存可先展示但标记“正在更新”；失败显示最后更新时间及重试。分享访客每次进入重新校验 token，失效立即清空页面内容。

链接绑定固定日期，始终读取该日期最新内容；标题和图片明确年月日，不固定称“今天”。图片是生成时快照，必须显示生成时间、三态及“安排可能变更，扫码查看最新”。图片本身不会随链接过期消失。二维码进入同一日期只读页；7 天只指链接有效期。

任一成员被移除时撤销该家庭所有既有分享链接；重新加入不恢复旧链接，可由有效成员重新分享。原负责人退出后日程保留，显示“负责人已离开，请重新安排”，管理员或创建人可重新指定；不得继续通知已退出人员。只读页展示相同提示。

新增通知负责人（排除操作者）；修改通知变更前后负责人并去重；取消、删除通知原负责人；完成及恢复待办通知当前负责人（均排除操作者）。保存成功与通知成功分开反馈。接收人须自行完成订阅，创建人不能代为授权；无法发送时提示“已保存，部分家人未收到通知，可分享安排”，不要求操作者替别人开启通知。平台模板、授权有效性及发送能力须在开发接入时按官方资料核验并真机验证。

## 11. 家庭名称与管理员移交

入口为「我的 → 家庭设置」。创建家庭的人是首任管理员，每个家庭只有一位管理员。代建家庭后，先邀请实际管理人加入，再移交给对方。

| 操作 | 当前管理员 | 普通成员 |
| --- | --- | --- |
| 修改家庭名称 | 可以。预填当前名称，去掉首尾空白后须为 1～20 个字，每 30 天可修改一次，取消保留原名 | 可查看，刷新后看到新名称 |
| 移交管理员 | 从本家庭其他有效成员中选择一人，核对接任人并二次确认 | 可接任 |
| 刷新邀请码、移除成员、解散家庭 | 可以。解散时须仅剩自己 | 无管理权限 |
| 查看成员、邀请家人 | 可以 | 可以 |

创建时的命名不计入次数。每次成功更名后满 30 天（720 小时）可再次修改，等待期间显示下次可修改的北京时间。保存原名不消耗次数，管理员移交后沿用同一家庭的等待期。既有家庭从首次记录到的成功更名开始计时。

只有管理员一人时，移交入口提示先邀请其他成员。确认框应显示接任成员名称，并说明对方将获得管理和解散权限，自己将成为普通成员。取消确认后可重新选择。提交时服务端重新检查双方身份和接任人的有效成员资格，角色和家庭所有者一次更新。原管理员保留家庭成员身份，日程操作按其普通成员、创建人或负责人身份判断。

验收时使用两个账号。先检查改名的空白、超长、取消和保存，再验证两端刷新后名称一致。移交前取消一次，确认角色未变；完成移交后，两端刷新应分别显示成员和管理员，只有接任人看到管理操作。接任人已被移除、来自其他家庭或原管理员重复提交时，拒绝请求并保持当前归属。

## 12. 接送确认与换人（拟新增）

适用于接孩子的日程。创建时指定当前负责人，初始显示「待确认 · 未接到」。本人点「我来接」后显示「已确认 · 未接到」。实际接到孩子时，由已确认的当前负责人点「我已接到」，显示「已确认 · 已接到」。管理员和创建人可以协调换人，确认接任和接到孩子须由当事人操作。此规则优先于第 10 节的通用完成权限；其他事项沿用原流程。

| 操作 | 谁可操作 | 全家看到的结果 |
| --- | --- | --- |
| 请人代接 | 当前负责人、创建人或管理员 | 从本家庭其他有效成员中选择一人。显示「当前负责人：爸爸」「等待奶奶答复」。保留爸爸原有的确认状态与责任 |
| 确认接任 | 受邀成员本人 | 同一次提交将负责人改为奶奶，接任状态为已确认，接送进度仍为未接到 |
| 暂时不能接 / 撤回邀请 | 受邀人可拒绝，发起人可撤回 | 清除待答复邀请，保留原负责人和确认状态，可再次邀请 |
| 已接到 | 已确认的当前负责人 | 记录接到时间与操作者，结束接送，同时关闭未答复的邀请 |

每条接送同时只允许一个待答复邀请。编辑页变更已有负责人也须经过接任确认。取消或删除安排后邀请失效；接任人离开家庭后不可接受。当前负责人已离开时显示「负责人已离开，待安排」，由创建人或管理员邀请接任者。服务端须按最新日程版本和成员身份校验；撤回、接到和接任并发时只接受有效操作。重复确认不产生第二次交接记录。

列表、详情及新生成的分享图片分别标明当前负责人、接任确认和接送进度；图片展示生成时的状态。详情记录谁发起、谁答复及谁接到。历史记录缺少确认信息时显示「无确认记录」，旧的已完成记录保留「已完成」原义。

验收示例：爸爸确认后邀请奶奶，奶奶答复前全家仍看到爸爸负责。奶奶拒绝后爸爸仍负责；再次邀请并接受后，只有奶奶能标记接到。若爸爸在等待期间先接到，奶奶随后打开旧邀请不能再接任。
